# Agent Note: 由运行持有的 broker 发现结果

Status: implemented

[English](2026-09-08-broker-run-discovery-cache.md) | 中文

## Problem

即使工作区元数据没有变化，重复的上下文发现仍会消耗远程请求配额。文件系统、子进程和原生工具分别持有 bridge 时，无法观察彼此的修改，也无法在配额耗尽后统一停止重试。

## Decision

一个由 Cordis 持有的 bridge 对应 Runtime 的运行租约。它持有修改代次、待完成写入、命令已派发标记，以及第一个经过验证的配额拒绝。文件系统 provider（提供者）最多保存 256 个发现结果，仅在同一无修改代次中填充缓存，并保留结构化的工作区拒绝。内部内容读取和修改检查始终获取实时信息。原生目录列表使用同一矛盾检查。

发现结果复用必须显式启用，且工作区由该运行独占。第一次命令或 stdin 派发会禁用复用，直到释放，包括成功完成的命令：已完成的 broker 会话可能留下继续修改文件的脱离后代进程。命令可以修改任意授权路径，因此使用整个代次失效，代替逐路径依赖追踪。

任何配额拒绝都会停止该 harness（框架）运行，即使其他操作可能具有更高限额。现有的 hook 取消机制中止当前 agent（智能体）活动，并在会话中记录配额消息，包括第一次模型请求之前的发现阶段；bridge 检查阻止后续请求。Python Runtime 独立于会话取消记录保留带类型的配额失败，并通过免配额控制路径完成远程运行。清理失败与原始拒绝分别报告。

## Alternatives considered

**提高预算。** 这会推迟耗尽，但仍然保留重复发现成本和重试循环。

**缓存所有 stat。** 内容读取和编辑检查需要实时元数据；广泛缓存可能掩盖并发修改或过期版本。

**各 provider 分别处理失效。** 原生工具和持久命令会话修改同一工作区，因此 provider 局部所有权会遗漏已有写入者。

**引入另一种取消事件。** Python 已经持有 broker 租约和终止失败。现有取消机制结合该所有者即可保留失败报告，无需增加会话结构变体。

## Consequences

第一条命令之前未发生修改的发现区间复用有界观察结果。命令之后的每次发现都保持实时，直到运行释放，因此整个运行的请求数取决于第一条命令和后续流量。存在不可观察写入者的工作区保持禁用缓存。本地检查不能证明已部署环境的所有权或远程清理；仍需托管环境验收。
